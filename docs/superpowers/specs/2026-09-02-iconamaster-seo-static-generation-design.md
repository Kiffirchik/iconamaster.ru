# SEO и статическая генерация Iconamaster

**Дата:** 2026-09-02
**Статус:** согласовано в чате
**Основной сайт:** `https://iconamaster.ru`

## 1. Цель

Сделать страницы `iconamaster.ru` полноценно доступными поисковым роботам без исполнения JavaScript, добавить корректные поисковые и социальные метаданные, установить Яндекс Метрику, создать коммерческую страницу расчистки храмовых росписей и закрепить единый адрес мастерской.

Существующий музейный визуальный стиль, каталог и клиентская навигация сохраняются. Сайт остаётся React/Vite-приложением, но каждая опубликованная каноническая страница получает готовый HTML при сборке.

## 2. Подтверждённые исходные данные

- Название: «Московская иконописная мастерская».
- Канонический домен: `https://iconamaster.ru`.
- Яндекс Метрика: счётчик `112185835`.
- Адрес: `Московская область, д. Брёхово, Ромашковая ул., 16`.
- Ссылка на Яндекс Карты: `https://yandex.com/maps/-/CTT2bAoq`.
- Основной канал консультаций: WhatsApp; телефон и email остаются видимыми альтернативами.
- Данные о наличии и категориях икон владелец обновляет отдельно. Эта работа не исправляет и не угадывает такие значения.

## 3. Текущее состояние

У production уже исправлены язык документа (`lang="ru"`) и базовый русский заголовок. Остальные маршруты обслуживаются одним HTML-каркасом, а контент подгружается из JSON после запуска JavaScript. `robots.txt` и `sitemap.xml` попадают под SPA-fallback и возвращают HTML. У страниц нет индивидуальных серверных метаданных и структурированных данных. Метрика в актуальном коде отсутствует.

Материал «Расчистка настенных храмовых росписей» опубликован как статья и содержит подтверждённые сведения о технологии, трёх выполненных объектах и среднем сроке работ для небольшого храма, но отдельной коммерческой страницы услуги нет.

## 4. Выбранная архитектура

### 4.1. Статическая генерация при сборке

Сборка состоит из клиентского Vite-бандла, небольшого серверного бандла для рендеринга React и шага предрендеринга.

1. Vite собирает обычные браузерные CSS и JavaScript.
2. Vite собирает серверную точку входа, которая умеет отрисовать существующее приложение для переданного пути и подготовленного content bundle.
3. Скрипт предрендеринга читает JSON из `public/content`, перечисляет все опубликованные канонические маршруты и создаёт для каждого путь вида `dist/client/<route>/index.html`.
4. Корневая страница записывается в `dist/client/index.html`.
5. В каждый HTML вставляются отрисованная разметка, метаданные и JSON-LD именно этой страницы.
6. Временный серверный бандл не попадает в клиентскую MTW-публикацию.

Физические HTML-файлы обслуживаются Apache через сгенерированные точные правила канонических маршрутов. Для каждого пути без завершающего слэша сервер внутренне открывает соответствующий `index.html`, а вариант со слэшем получает 301 на канонический путь. Это предотвращает автоматический `DirectorySlash`-редирект к URL, который расходится с canonical. После покрытия всех канонических маршрутов общий SPA-fallback больше не нужен на MTW: старые псевдонимы получают серверные постоянные редиректы на канонические пути, а неизвестный путь возвращает настоящий статус 404 и отдельный статический документ ошибки. Это не позволяет ошибочному URL сначала отдавать HTML главной страницы со статусом 200.

### 4.2. Гидратация без исчезновения HTML

Предрендеренная разметка остаётся видимой, пока браузер загружает JSON-контент. После успешной загрузки React гидратирует ту же страницу. HTML содержит маркер канонического пути; гидратация разрешена только когда маркер совпадает с маршрутом, вычисленным клиентом. При несовпадении React выполняет обычный чистый рендер вместо некорректной гидратации. Это исключает замену полезного HTML экраном «Загружаем коллекцию…» и сохраняет существующую навигацию без перезагрузки.

Если JSON загрузить не удалось, клиент показывает уже существующее диагностическое состояние с повторной попыткой. Ошибка одного контентного запроса не должна оставлять пустой документ.

При переходах внутри приложения клиентский SEO-контроллер обновляет `title`, description, canonical, Open Graph и JSON-LD, чтобы метаданные не оставались от предыдущего маршрута.

### 4.3. Перечень генерируемых маршрутов

- `/`;
- `/collection`;
- `/icons/<slug>` для каждой опубликованной иконы;
- все опубликованные информационные страницы из `pages.json`;
- `/raschistka-hramovyh-rospisey`;
- `/articles`;
- `/articles/<slug>` для каждой опубликованной статьи;
- `/video`;
- `/contacts`.

Псевдонимы не включаются в Sitemap и не получают второй документ: для них генерируются правила HTTP 301 на соответствующий канонический маршрут. Неизвестные пути получают HTTP 404 и `noindex,follow`.

## 5. Поисковые и социальные метаданные

Единая библиотека SEO-описаний принимает маршрут и content bundle и возвращает:

- индивидуальный `title`;
- индивидуальный `meta name="description"`;
- абсолютный `link rel="canonical"`;
- `og:title`, `og:description`, `og:url`, `og:type`, `og:locale`;
- абсолютный `og:image`, когда у материала есть изображение;
- `twitter:card`, `twitter:title`, `twitter:description` и изображение;
- директиву `robots`; неизвестные страницы получают `noindex,follow`.

Описание икон строится из названия и нормализованного описания с ограничением длины. Описание статьи использует `summary` или вступление. Для основных разделов и услуги используются редакторские формулировки. Метаданные не должны содержать пустые значения, HTML или повтор заголовка без дополнительного смысла.

## 6. Структурированные данные

Каждый документ получает безопасно сериализованный `application/ld+json` с абсолютными URL.

- Главная и контакты: `LocalBusiness` с названием, телефоном, email, адресом и ссылкой на карту.
- Коммерческая страница росписей: `Service`, связанный с мастерской как исполнителем.
- Статьи: `Article` с заголовком, описанием и изображением.
- Карточки икон: `VisualArtwork`; `Product` и `Offer` добавляются только при наличии пригодных данных о продаже. Пустое или неоднозначное наличие не преобразуется в ложный статус Schema.org.
- Все внутренние страницы: `BreadcrumbList`.

JSON-LD не должен заявлять лицензии, аттестации, рейтинги, наличие или цены, которых нет в проверенных данных.

## 7. Robots и Sitemap

Сборка создаёт настоящий текстовый `robots.txt`:

```text
User-agent: *
Allow: /
Disallow: /corona/
Disallow: /captcha/
Sitemap: https://iconamaster.ru/sitemap.xml
```

`sitemap.xml` создаётся из того же перечня канонических опубликованных маршрутов, что и HTML. В карту не попадают псевдонимы, unpublished-записи и служебные пути. Искусственный `lastmod` не добавляется: дата появляется только тогда, когда источник начнёт хранить достоверную дату изменения.

`.htaccess` сначала применяет точные правила канонических HTML-маршрутов и редиректы псевдонимов, затем сохраняет исключение для остальных реальных файлов и каталогов и завершает обработку настоящим 404 вместо возврата корневого документа. Существующие служебные каталоги Corona остаются доступны по своим реальным путям.

`robots.txt`, `sitemap.xml` и `404.html` должны иметь правильное содержимое и статус ответа на production и не перехватываться правилами маршрутизации.

## 8. Яндекс Метрика

На все страницы устанавливается актуальный асинхронный код счётчика `112185835` с включёнными `clickmap`, `trackLinks`, `accurateTrackBounce` и `webvisor`. Добавляется `noscript`-пиксель.

Клики по WhatsApp, телефону и email отправляют события `contact_whatsapp`, `contact_phone` и `contact_email`; основной CTA страницы росписей дополнительно отправляет `murals_consultation`. Отсутствие или блокировка `ym` не должна мешать переходу по ссылке. События используются только как измерение обращения; фактическая продажа или договор не считаются автоматически.

## 9. Коммерческая страница расчистки росписей

Канонический путь: `/raschistka-hramovyh-rospisey`.

Страница использует только сведения, подтверждённые существующим материалом:

- расчистка настенной храмовой живописи от копоти и загрязнений;
- укрепление основы, штукатурного и красочного слоя в составе описанного процесса;
- восстановление повреждённых участков художниками-иконописцами;
- работа небольшими участками;
- применение подвижных конструкций типа «тура»;
- средний срок от одного до двух месяцев для небольшого храма;
- возможность не прекращать функционирование храма при описанном способе организации;
- примеры храмов на Речном вокзале, в Сходне и Химках.

Структура страницы:

1. коммерческий заголовок и краткое ценностное предложение;
2. фотография и CTA «Получить предварительную консультацию»;
3. блок «Что входит в работу»;
4. блок «Как проходит работа» без неподтверждённых обещаний о смете или диагностике;
5. три подтверждённых примера с имеющимися фотографиями;
6. сроки и организация работ;
7. CTA с тематическим сообщением WhatsApp, телефоном и email;
8. ссылка на подробную исследовательскую статью.

Материал хранится в `pages.json` как опубликованная страница с шаблоном услуги и структурированными секциями. Схема контента явно разрешает этот шаблон, а специализированный компонент отвечает только за коммерческую композицию и CTA; фактические тексты и изображения остаются в данных.

Страница добавляется в основную навигацию и футер обычными `href`, чтобы ссылка была доступна роботу и без JavaScript. Статья о расчистке получает внутреннюю ссылку на коммерческую страницу.

## 10. Единый адрес

`contacts.json` становится единственным структурированным источником адреса и ссылки на карту. В нём добавляются `mapUrl` и объект `address` с полями `display`, `streetAddress`, `addressLocality`, `addressRegion` и `addressCountry`. Валидатор контента проверяет их типы и обязательные значения. Страница контактов показывает полный адрес и кнопку перехода в Яндекс Карты. Футер показывает краткую географию мастерской.

Существующие тексты проезда в `pages.json` приводятся к формулировке `Московская область, д. Брёхово, Ромашковая ул., 16` и используют одну ссылку на карту. Упоминания Зеленограда как географии выполненного объекта или ориентира не изменяются.

После публикации проводится проверка карточек Яндекс Карт и 2ГИС. Если доступ владельца к внешней карточке доступен в браузере, адрес исправляется там. Если сервис требует отдельного входа или подтверждения владельца, изменение исходного сайта считается выполненным, а внешний шаг фиксируется как требующий действия владельца; карточка не подменяется неподтверждённой публичной правкой.

## 11. Тестирование

Изменения выполняются через тесты. Проверки должны доказывать:

1. `lang="ru"` и отсутствие `Prototype` в исходном и собранном HTML;
2. наличие полного видимого контента в HTML до выполнения JavaScript;
3. генерацию каждой опубликованной канонической страницы, 301 для каждого псевдонима и настоящий 404 для неизвестного пути;
4. отсутствие unpublished-записей и псевдонимов в Sitemap;
5. корректность XML и robots;
6. уникальные title, description, canonical и Open Graph для ключевых типов страниц;
7. валидно сериализованный JSON-LD без ложного Offer;
8. счётчик `112185835` и безопасные события контактных ссылок;
9. существование коммерческой страницы, её CTA, изображения, внутренние ссылки и подтверждённые формулировки;
10. единый адрес в данных, контактах, HTML и LocalBusiness;
11. сохранение существующего поведения навигации, каталога, галерей и контактов;
12. успешные Sites- и MTW-сборки.

Перед завершением выполняется полный `npm run verify`, локальный просмотр основных страниц на desktop и mobile и проверка собранных файлов отдельным статическим сервером.

## 12. Публикация и откат

После полной проверки:

1. фиксируется точный исходный commit;
2. commit отправляется в `https://github.com/Kiffirchik/iconamaster.ru`;
3. только после успешного push создаётся MTW-сборка;
4. текущий document root сохраняется отдельной rollback-копией и архивом;
5. новая сборка публикуется атомарной заменой каталога с сохранением Corona, `config.php`, `uploads` и `captcha`;
6. production проверяется по главной, коммерческой странице, карточке иконы, статье, контактам, `robots.txt`, `sitemap.xml`, Метрике и административному маршруту;
7. при критической ошибке выполняется обратное переименование на сохранённый document root.

## 13. Критерии готовности

Работа завершена, когда production отдаёт готовый русскоязычный HTML для всех опубликованных канонических маршрутов; у страниц есть корректные индивидуальные метаданные и JSON-LD; `robots.txt` и `sitemap.xml` являются настоящими файлами; счётчик 112185835 присутствует; коммерческая страница расчистки доступна из навигации; полный адрес Брёхово показан единообразно; все автоматические и визуальные проверки пройдены; исходники отправлены в GitHub; rollback сохранён.

Редактирование категорий и статусов наличия 50 икон не входит в критерии готовности этой работы.
