# Универсальная установка Iconamaster в Windows

Дата: 1 сентября 2026 года  
Статус: согласованная архитектура, ожидает просмотра спецификации пользователем

## 1. Цель

Подготовить проект Iconamaster к воспроизводимой работе на любой поддерживаемой Windows-машине без привязки к каталогам текущего компьютера. Новый разработчик или чистая рабочая среда должны получить проект из GitHub, запустить один PowerShell-скрипт и получить либо готовое проверенное окружение, либо точный список недостающих компонентов и команд для исправления.

Решение использует согласованный гибридный подход:

- по умолчанию скрипт проверяет среду, устанавливает npm-зависимости внутри проекта и запускает проверку проекта;
- системные компоненты автоматически устанавливаются только при явном флаге `-InstallPrerequisites`;
- режим `-CheckOnly` не изменяет ни систему, ни проект;
- инструменты публикации и миграции проверяются отдельно и не являются обязательными для обычной разработки.

Изменения относятся к локальной разработке и документации. Они публикуются в GitHub, но сами по себе не требуют выкладки сайта на MTW.

## 2. Поддерживаемая платформа

На этом этапе поддерживается только:

- Windows 10 или Windows 11;
- Windows PowerShell 5.1 и PowerShell 7+;
- файловая система с поддержкой обычных каталогов проекта; junction или symlink для `node_modules` не требуется.

macOS, Linux, WSL и контейнерная установка не входят в текущий объём. Скрипт должен завершаться с понятным сообщением, если его запускают в неподдерживаемой среде.

## 3. Основной интерфейс

В корне репозитория создаётся `setup.ps1`. Все пути внутри него вычисляются от `$PSScriptRoot`; текущий каталог запуска не имеет значения. Скрипт можно запускать из пути с пробелами и с другим именем пользовательского профиля.

Поддерживаемые сценарии:

```powershell
# Проверить среду, установить npm-зависимости и полностью проверить проект
.\setup.ps1

# Только диагностика, без установки и изменения файлов
.\setup.ps1 -CheckOnly

# При необходимости поставить основные системные компоненты через winget,
# затем установить зависимости и проверить проект
.\setup.ps1 -InstallPrerequisites

# Дополнительно проверить инструменты публикации на MTW
.\setup.ps1 -ForDeployment

# Дополнительно проверить закреплённый FFmpeg для повторной миграции медиа
.\setup.ps1 -ForMigration
```

Флаги `-ForDeployment` и `-ForMigration` можно сочетать с `-CheckOnly` или обычным запуском. `-InstallPrerequisites` нельзя сочетать с `-CheckOnly`: скрипт должен отклонить противоречивую комбинацию до любых изменений.

## 4. Обязательные компоненты

### 4.1. Обычная разработка и сборка

Обязательны:

- Git for Windows;
- Node.js `^20.19.0 || >=22.12.0`;
- npm 10 или новее;
- доступ в интернет при первом `npm ci`.

Диапазон Node.js определяется фактическими требованиями Vite и `@vitejs/plugin-react`. Он фиксируется в `package.json` через `engines`. Используемый менеджер пакетов фиксируется через `packageManager`, а воспроизводимая установка выполняется только командой `npm ci` по существующему `package-lock.json`.

### 4.2. Публикация на MTW

Для режима `-ForDeployment` дополнительно проверяются:

- `ssh`;
- `scp`;
- `tar`.

Эти команды нужны только для публикации и отката на MTW. Обычная установка проекта не должна завершаться ошибкой из-за их отсутствия.

OpenSSH Client является компонентом Windows, а не обычным npm-пакетом. Первая версия установщика не включает его автоматически и не запрашивает административные права. При отсутствии `ssh` или `scp` скрипт показывает точную инструкцию установки штатного компонента Windows. Аналогично для отсутствующего `tar` выводится безопасная инструкция, а не скачивается неизвестный бинарный файл.

### 4.3. Повторная миграция контента

Для режима `-ForMigration` дополнительно проверяется FFmpeg. Текущий мигратор требует не просто любую команду `ffmpeg`, а конкретную версию и SHA-256, закреплённые в `tests/fixtures/migration/editorial-cover-assets.json`.

Поэтому FFmpeg:

- не устанавливается автоматически через `winget`;
- не нужен для запуска сайта, тестов содержимого или обычной сборки;
- считается готовым только после проверки версии и контрольной суммы по существующему контракту мигратора;
- при несовпадении получает отдельное диагностическое сообщение с указанием на fixture и документацию.

## 5. Гибридная установка системных компонентов

Без `-InstallPrerequisites` скрипт не меняет системное окружение. Если Git, Node.js или npm отсутствуют либо имеют неподдерживаемую версию, запуск завершается до `npm ci` и показывает найденную версию, требуемую версию и следующий шаг.

С `-InstallPrerequisites` скрипт:

1. проверяет наличие `winget`;
2. при отсутствии Git устанавливает пакет `Git.Git`;
3. при отсутствии или неподдерживаемой версии Node.js устанавливает подходящий официальный пакет Node.js LTS;
4. обновляет представление `PATH` в текущем процессе либо сообщает, что требуется новый терминал;
5. повторно проверяет версии;
6. только после успешной повторной проверки продолжает установку проекта.

Каждый вызов `winget` использует точный идентификатор пакета, согласие с условиями источника и не подтверждает установку других пакетов. Скрипт не удаляет существующие версии программ, не изменяет политики PowerShell и не запрашивает сохранение логинов, паролей или SSH-ключей.

Если `winget` отсутствует, скрипт ничего не скачивает обходным способом и выводит официальные ручные шаги.

## 6. Поведение режимов

### 6.1. `-CheckOnly`

Режим выполняет только чтение:

- определяет корень проекта;
- проверяет PowerShell, Git, Node.js и npm;
- проверяет соответствие Node.js и npm объявленным версиям;
- проверяет наличие `package.json` и `package-lock.json`;
- проверяет, что lockfile совместим с `npm ci`;
- сообщает о состоянии локальных зависимостей, но не создаёт `node_modules`;
- запускает проверку переносимости отслеживаемых файлов;
- при дополнительных флагах проверяет deployment- или migration-инструменты.

Он не вызывает `winget`, `npm ci`, сборку, форматирование или команды, записывающие файлы.

### 6.2. Обычный запуск

Обычный запуск после успешной проверки среды:

1. выполняет `npm ci` в каталоге проекта;
2. запускает проверку переносимости;
3. выполняет `npm run verify`;
4. печатает краткий итог с версиями и результатами.

Если любой шаг завершился ошибкой, скрипт немедленно останавливается с ненулевым кодом. Он не маскирует ошибку и не сообщает об успешной готовности.

`npm ci` должен создавать обычный локальный каталог `node_modules`. Существующий на одной из рабочих машин junction не является частью репозитория и не рассматривается как поддерживаемый способ установки.

## 7. Проверка переносимости путей

Создаётся отдельный проверяемый скрипт Node.js, запускаемый через npm-команду `check:portability`. Он анализирует только файлы, отслеживаемые Git, и не сканирует `.git`, `node_modules`, `dist`, резервные копии публикаций или пользовательские секреты вне репозитория.

Проверка отклоняет машинозависимые локальные ссылки, включая:

- пути пользовательских профилей вида `C:\Users\имя\...` и `C:/Users/имя/...`;
- `file:///C:/...`;
- ссылки на `AppData`, локальные временные каталоги и каталоги текущей рабочей копии;
- операционные скрипты, полагающиеся на соседнюю рабочую копию или junction.

Допустимы:

- пути, вычисляемые во время выполнения от `$PSScriptRoot`, `import.meta.url` или корня Git;
- URL сайта и внешних сервисов;
- документированные серверные пути MTW вида `/www/vhosts/...`, если они не используются как локальный Windows-путь;
- синтетические Windows-пути внутри тестовых fixtures, явно предназначенных для проверки детектора.

Исключения должны быть узкими, находиться в коде проверки и иметь объясняющий комментарий. Общего отключения проверки для `docs` или `scripts` не допускается.

Найденная в историческом плане ссылка на локальный файл `new admid creds.txt` заменяется нейтральным обозначением файла вне репозитория. Сам файл с учётными данными не перемещается в Git и не читается установщиком.

## 8. Документация

Корневой `README.md` становится основной точкой входа и содержит:

- назначение проекта;
- поддерживаемую Windows-платформу;
- минимальные версии;
- быстрый старт через `setup.ps1`;
- различие между `-CheckOnly`, обычным запуском и `-InstallPrerequisites`;
- отдельные требования для MTW и миграции;
- основные npm-команды;
- правило хранения секретов вне Git;
- ссылку на подробную инструкцию публикации, если она уже существует.

Технические детали можно вынести в `docs/windows-setup.md`, но пользователь не должен собирать основной сценарий из нескольких документов. Сообщения самого скрипта и документация используют одинаковые названия флагов и одинаковые версии.

`package.json` дополняется:

- `engines.node`;
- `engines.npm`;
- `packageManager`;
- npm-командой `check:portability`;
- включением проверки переносимости в общий `verify`.

## 9. Безопасность и секреты

Установщик не:

- читает `new admid creds.txt` или другие файлы с логинами и паролями;
- выводит значения переменных окружения, SSH-ключей или учётных данных;
- записывает секреты в `.npmrc`, Git-конфигурацию или документы;
- подключается к MTW;
- публикует сайт;
- меняет глобальную политику выполнения PowerShell.

Если локальная политика запрещает запуск `setup.ps1`, документация предлагает разовый запуск процесса с `-ExecutionPolicy Bypass -File`, не изменяя системную политику постоянно.

## 10. Обработка ошибок

Каждая ошибка содержит:

- название провалившейся проверки;
- найденное состояние или версию, если это безопасно;
- ожидаемое состояние;
- одну конкретную следующую команду или действие;
- ненулевой код завершения.

Частично выполненная установка npm может быть безопасно повторена, потому что следующий запуск снова использует `npm ci`. Установщик не удаляет каталоги проекта вручную и не применяет `git reset`, `git clean` или иные разрушительные команды.

Ошибка дополнительного deployment- или migration-инструмента считается ошибкой только если пользователь запросил соответствующий режим.

## 11. Тестирование

Реализация ведётся через тесты. Минимальный набор автоматических проверок:

1. проверка параметров и несовместимой комбинации `-CheckOnly -InstallPrerequisites`;
2. запуск `setup.ps1 -CheckOnly` из другого текущего каталога;
3. запуск из копии проекта, путь к которой содержит пробелы;
4. корректное принятие поддерживаемых версий Node.js и npm;
5. понятный отказ для отсутствующей и устаревшей версии без системной установки в тесте;
6. отсутствие вызова `winget` без явного `-InstallPrerequisites`;
7. обнаружение пользовательского абсолютного пути проверкой переносимости;
8. отсутствие ложной ошибки для разрешённого серверного пути MTW и тестового fixture;
9. полная команда `npm run verify`;
10. чистая установка из архивной или клонированной копии без junction `node_modules`.

В тестах системные команды обнаружения и установки должны быть подменяемыми либо проверяться через изолированный тестовый интерфейс. Автотесты не должны реально устанавливать Git, Node.js, OpenSSH или FFmpeg на машине разработчика.

## 12. Критерии готовности

Работа готова, когда:

- в отслеживаемых файлах нет ссылок на профиль и рабочие каталоги текущего компьютера;
- `setup.ps1 -CheckOnly` не изменяет проект и завершается корректно на поддерживаемой среде;
- обычный `setup.ps1` создаёт локальные зависимости через `npm ci` и успешно выполняет `npm run verify`;
- режим автоматической установки невозможен без явного флага;
- deployment- и migration-зависимости отделены от обычной разработки;
- установка проверена из пути с пробелами и без junction `node_modules`;
- README описывает все обязательные и дополнительные компоненты;
- полный набор тестов проходит;
- точный проверенный исходный код зафиксирован коммитом и отправлен в `https://github.com/Kiffirchik/iconamaster.ru`;
- production-сайт не изменён этой задачей.

## 13. Вне объёма

- поддержка macOS, Linux, WSL и Docker;
- автоматическая установка или обновление OpenSSH, `tar` и FFmpeg;
- хранение либо перенос учётных данных;
- запуск публикации на MTW из `setup.ps1`;
- изменение контента или дизайна сайта;
- автоматическое обновление системных компонентов без явного согласия пользователя.

## 14. Итоговый результат

Результатом станет Windows-ориентированный, воспроизводимый процесс установки с одним корневым скриптом, явными безопасными режимами и автоматической защитой от новых машинозависимых путей. Для повседневной разработки потребуется только основной набор Git, Node.js и npm; публикация и повторная миграция останутся отдельными осознанными сценариями.
